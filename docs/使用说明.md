# uav_mavlink_pkg 使用说明

> 通用无人机五层解耦 ROS 软件包 — 不绑定任何特定比赛或场景

---

## 1. 设计理念

本软件包将无人机自主飞行系统按「感知→定位→规划→决策→执行」五层严格解耦：

- **每层独立节点**，层间仅通过 ROS Topic/Service 通信
- **状态机驱动** 任务流程，不阻塞 ROS 事件循环
- **执行层纯硬件桥接**，赛题无关，换赛题不改
- **公共层集中管理** 接口常量，避免魔法字符串

框架历经 **五届赛事实飞迭代**：第 27 届 CRAIC 国赛（脚本式雏形）→ 2025 H 题「野生动物巡查」（脚本式延续，新增地面站通信与全覆盖规划）→ 2024 D 题「立体货架盘点」（**第一次整体重构，五层解耦成型**）→ 2023 G 题「空地协同智能消防」（五层演进）→ 2026 D 题「搜救飞行器」（**完善版**，本仓库参考实现）。完整演进记录见仓库 [CHANGELOG.md](../CHANGELOG.md)。适配新任务场景只需修改感知层 + 规划层 + 决策层。

## 2. 五层职责与边界

### 2.1 职责与禁止行为

| 层级 | 职责 | 🚫 禁止行为 |
|------|------|------------|
| **感知层** | 传感器接入、图像/目标检测、特征提取 | 不得订阅执行层指令；**不得直接控制硬件** |
| **定位层** | 位姿估计、坐标变换、环境地图更新 | 不得订阅决策层状态；不得发布控制指令 |
| **规划层** | 全局/局部路径生成、航点插值、任务序列编排 | 不得直接调用飞控接口；不得感知原始图像 |
| **决策层** | 状态机、任务调度、异常恢复、行为选择 | 不得直接处理图像；只做逻辑决策 |
| **执行层** | 控制指令下发、执行器驱动、硬件抽象 | 不得做规划/决策；不得订阅原始图像 |

### 2.2 换赛题改动力度

| 层 | 换赛题时 |
|------|:---:|
| 感知层 | **必改** — 替换检测算法 |
| 定位层 | 🟢 不改 — 纯硬件绑定 |
| 规划层 | **必改** — 替换路径策略 |
| 决策层 | **必改** — 重写状态流转 |
| 执行层 | 🟢 不改 — 纯硬件桥接 |
| 公共层 | 🟡 场地常量改，接口名不动 |
| 安全层 | 🟡 只调边界常量 |
| 记录层 | 🟢 不改 |

## 3. 目录结构

> 本仓库发布**通用骨架**：下述结构中 `common/`、`execution/`、`localization/`、`safety/`、`logging/` 与接口定义（msg/srv/action）均随仓库提供；`perception/`、`planning/`、`decision/` 为业务层扩展点（设计规范与参考实现见 [框架设计文档.md](框架设计文档.md)），按第 9 章指南填充。

```
uav_mavlink_pkg/
├── msg/                    # 自定义消息（12 个，随仓库发布）
├── srv/                    # 自定义服务（5 个，随仓库发布）
├── action/                 # 自定义动作（Takeoff，随仓库发布）
├── scripts/
│   ├── common/             # 公共层：接口常量 + 路径规划 ★随仓库发布
│   ├── perception/         # 感知层：相机 + 检测器（业务扩展点）
│   ├── localization/       # 定位层：状态估计 + TF + 降落定位 ★随仓库发布
│   ├── planning/           # 规划层：全局 + 局部 + 任务透传（业务扩展点）
│   ├── decision/           # 决策层：状态机 + 行为选择 + 安全 + 通信（业务扩展点）
│   ├── execution/          # 执行层：飞控 + 舵机 + 降落 + 蜂鸣器 ★随仓库发布
│   ├── safety/             # 安全层：独立监控旁路 ★随仓库发布
│   └── logging/            # 记录层：rosbag + JSONL ★随仓库发布
├── launch/
│   └── skeleton_minimal.launch  # 骨架最小启动（随仓库发布）
├── config/
│   └── skeleton_params.yaml     # 骨架通用参数（随仓库发布）
├── 框架设计文档.md          # 位于仓库 docs/ 目录
└── 使用说明.md              # 位于仓库 docs/ 目录（本文件）
```

## 4. 编译与启动

### 4.1 编译

```bash
cd ~/ctrl_ws
catkin_make -DCATKIN_WHITELIST_PACKAGES="uav_mavlink_pkg"
source devel/setup.bash
```

编译成功后，自定义消息/服务/动作自动生成。修改 `.msg`/`.srv`/`.action` 后需重新编译。

### 4.2 启动方式

```bash
# 骨架最小启动（执行层 + 定位层 + 安全旁路 + 记录层，随本仓库发布）
# 无需编写任何业务代码即可验证框架链路; fc_serial_port 按实际设备修改
roslaunch uav_mavlink_pkg skeleton_minimal.launch fc_serial_port:=/dev/ttyXXX
```

以下完整任务启动文件属于完整参考实现（含业务层节点，未随骨架发布，仅作编排示例）：

```bash
# 最小启动（仅飞控 + 定位），调试底盘用
roslaunch uav_mavlink_pkg uav_data.launch

# 任务启动（完整链路），以 D 题为例
roslaunch uav_mavlink_pkg uav_d_search_rescue.launch

# D 题纯航线测试（无感知层）
roslaunch uav_mavlink_pkg uav_d_search_rescue_no_detect.launch

# G 题完整任务（参考实现）
roslaunch uav_mavlink_pkg uav_g_firefighting.launch

# G 题纯航线测试（无感知层）
roslaunch uav_mavlink_pkg uav_g_firefighting_no_fire.launch
```

> 换任务场景时只需新增对应的 `config/*.yaml` 和 `launch/*.launch`，并按第 9 章指南填充业务节点。

### 4.3 常用 launch 参数

```bash
# D 题（当前）常用参数（串口按实际设备修改）
roslaunch uav_mavlink_pkg uav_d_search_rescue.launch \
    use_mock:=false \                 # 地面站串口模式（true=无地面站模拟）
    auto_start:=false \               # 自动起飞（无地面站时 true）
    flight_height:=1.0 \              # 飞行高度 (m)
    serial_port:=/dev/ttyXXX \        # 地面站串口（按实际设备修改）
    fc_serial_port:=/dev/ttyXXX \     # 飞控串口（按实际设备修改）
    debug_mode:=true                   # 感知层 debug 图

# G 题（参考实现）常用参数
roslaunch uav_mavlink_pkg uav_g_firefighting.launch \
    flight_height:=1.4 \              # 巡逻高度 (m)
    mission_timeout:=360.0 \          # 任务超时 (s)
    xy_tolerance:=0.10 \              # 航点到达容差 (m)
    fc_serial_port:=/dev/ttyXXX \     # 飞控串口（按实际设备修改）
    debug_mode:=true                   # 感知层 debug 图
```

## 5. 框架设计规范速查（10 问）

### Q1：为什么感知层不能直接发控制指令？

防止图像误检或单帧异常导致无人机瞬间失控。感知层只发布检测目标，由决策层统一决策后下发控制指令，形成安全隔离。

### Q2：为什么安全监控要做成两层？

| 节点 | 所属层级 | 监控方式 | 作用 |
|------|----------|----------|------|
| `safety_monitor_node` | 决策层内 | 订阅任务状态 + UavState | 任务级安全（超时/边界） |
| `safety_supervisor_node` | 独立进程 | **直接**订阅 `/localization/uav_state` | 旁路监控，发布 `SafetyEvent(CRITICAL)` |

安全链路：`safety_supervisor_node` 独立于状态机检测危险（超界/定位丢失）→ 发布 CRITICAL 事件 → `mission_state_machine_node` 响应并转 LANDING。它本身不直接控制飞控；若状态机已卡死，需遥控器接管。

### Q3：为什么起飞用 Action 而不是 Service？

起飞是**长时间运行**任务，需要进度反馈和可抢占取消。Action 天然支持 `feedback` 和 `cancel`，Service 不适合异步长任务。

### Q4：新增一个比赛任务，最少改哪几个文件？

最少改 3 处：

1. **`common/path_planner.py`** — 生成新任务的全局航点
2. **`decision/mission_state_machine_node.py`** — 新增状态机分支
3. **按需新增感知节点** — 如 `fire_detector_node.py` → `xxx_detector_node.py`

执行层（飞控、舵机、降落、蜂鸣器）可直接复用。

### Q5：换一款飞控需要改哪些？

取决于飞控通信协议：如果仍是 MAVLink 兼容（如 ZMO-M4、Pixhawk 系列），只需改 `flight_controller_node.py` 的串口参数和 MAVLink 命令映射。如果飞控使用私有协议，则需重写 `flight_controller_node.py` 的通信部分，但 ROS 接口（`/execution/cmd_pose` 等话题）保持不变。

### Q6：新增一种传感器（如激光雷达），放在哪一层？

**感知层**。新建节点（如 `lidar_obstacle_node.py`），发布检测结果到 `/perception/obstacles`，由规划层订阅使用。不改其他层。

### Q7：`Waypoint.msg` 里的 `type` 字段是干什么用的？

告诉状态机到这个航点后做什么。当前框架的 type 枚举（在 `uav_interfaces.py`）：

| 值 | 名称 | 行为 |
|:--:|------|------|
| 0 | HOVER_DETECT | 悬停检测点 |
| 1 | PATROL | 巡逻点 |
| 4 | LAND | 降落点 |
| 6 | FIRE_APPROACH | 接近火源（G 题） |
| 7 | FIRE_DESCEND | 下降到投弹高度（G 题） |
| 8 | FIRE_DROP | 投弹点（G 题） |

换赛题时扩展此枚举即可让每个航点携带不同任务语义。

D 题另有 `DWaypointType` 枚举：`SEARCH=1`（蛇形搜索点）、`DROP_APPROACH=10`（投放接近点）、`DROP_DESCEND=11`（投放下降点）、`GUIDE=20`（引导航点）、`LAND=4`（降落点）。

### Q8：怎么通过 rostopic 确认状态机正常跳转？

```bash
rostopic echo /decision/mission_status
```

关注 `state`、`current_cell`、`message`、`progress` 字段是否按预期变化。

### Q9：出现异常时，先看 `/safety/event` 还是 `/decision/mission_status`？

**先看 `/safety/event`**。它记录了异常等级（INFO/WARN/ERROR/CRITICAL）、来源节点。然后再结合 `/decision/mission_status` 看状态机的响应是否正确。

### Q10：为什么 MAVLink 发送用 10Hz 流式而不是"发一次等到达"？

单次发送模式如果飞控没收到那一次丢包，就永远等不到 → 断连。10Hz 流式发送：飞控每 100ms 收到一帧，丢一帧无所谓，下一帧 100ms 后就到。这是旧框架 30-40 格断连问题的根因解决方案，也是本框架最核心的设计决策。

## 6. 核心数据流（通用模式）

```
感知层 ──检测结果──▶ 决策层 ──位姿指令──▶ 执行层 ──MAVLink──▶ 飞控
                           │
定位层 ──UavState──▶ 决策层
                           │
规划层 ──WaypointList──▶ 决策层
                           │
                    ┌──────┴──────┐
│ 行为选择器   │──laser_cmd──▶ 执行层 PWM（激光/舵机）
│ 安全监控     │──SafetyEvent──▶ 状态机
│ 外部通信     │──UART 蓝牙──▶ 地面站（STM32+TJC）
                    └─────────────┘
```

**关键约束**：决策层的 `mission_state_machine_node` 是**唯一**有权发飞行指令的节点。感知层只发布检测结果、规划层只发布航点列表、执行层只负责下行透传——没有任何其他节点可以直接控制无人机。

```

Step 2: 场地常量    → common/uav_interfaces.py      修改场地尺寸 + 新增状态枚举 + Waypoint type
Step 3: 状态机      → decision/mission_state_machine_node.py  重写状态流转
Step 4: 感知检测    → perception/xxx_detector_node.py         新检测节点
Step 5: 行为映射    → decision/behavior_selector_node.py     状态→动作映射
Step 6: 通信协议    → decision/xxx_comm_node.py             新外部通信（按需）
Step 7: 参数配置    → config/xxx.yaml + launch/xxx.launch   新赛题参数
```

|------|------------------------|------------------------|------------------------|

## 10. 框架性能特性

| 特性 | 实现方式 | 效果 |
|------|---------|------|
| 抗 MAVLink 丢包 | 10Hz Timer 持续流式发送位姿命令 | 丢一帧不碍事，100ms 后下一帧到 |
| ROS spin 不阻塞 | Timer 驱动状态机，不在回调中 sleep | 心跳/位置报告持续被处理 |
| 多外部通信 | 每个通信目标独立节点 + 独立线程 | 互不干扰，可按需启停 |
| 安全冗余 | 双安全监控（决策层 + 旁路发布 CRITICAL） | 危险事件由状态机响应转 LANDING |
| 赛后复盘 | rosbag + JSONL 双格式记录 | 可离线回放分析 |

## 11. 常见问题

### 编译报错找不到自定义消息
先 `catkin_make` 生成消息头文件。首次编译报错的话，再跑一次即可。

### 起飞后状态机不推进
检查 `flight_height` 参数是否与实际爬升高度匹配。D 题起飞后还需等待 QR 解码成功（15s 超时兜底默认出口）才会进入巡逻；G 题在 `z >= flight_height - 0.2m` 后直接开始。

### Python 文件在 Orange Pi 上报 SyntaxError
Windows 上编辑的 `.py` 可能带 UTF-8 BOM 头。用以下方式写入避免：
```powershell
[System.IO.File]::WriteAllText("path", $content, [System.Text.UTF8Encoding]::new($false))
```

### 如何确认节点间通信正常
```bash
rostopic hz /execution/cmd_pose    # 应接近 10Hz
rostopic hz /localization/uav_state # 应接近 FAST-LIO 发布频率
```

### 状态机卡死时如何自救
1. 先查 `/safety/event` 确认异常等级
2. 再看 `/decision/mission_status` 确认当前状态
3. `safety_supervisor_node` 独立旁路发布 CRITICAL 事件后，状态机会转 LANDING 紧急降落；若状态机本身已卡死，用遥控器拨杆接管（非 GUIDED 时状态机停发指令让出控制权）
