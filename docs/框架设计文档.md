## 2. 飞行数据流（核心链路）

```
FAST-LIO ──/Odometry──▶ flight_controller ──vision_position_estimate──▶ 飞控 EKF
                                       ┌── 10Hz 持续流式发送 ──┐
mission_state_machine ──/cmd_pose──▶ flight_controller ──set_position_target──▶ 飞控
                                       └── 天然抗丢包 ────────┘

mission_state_machine ◀──/localization/uav_state── state_estimator (XY:雷达 + Z:飞控)
mission_state_machine ◀──/perception/qr_result── qr_code_detector ◀──/camera/image_raw── camera_node
mission_state_machine ◀──/perception/target_bucket── fusion_target_detector ◀──/camera/image_raw── camera_node

mission_state_machine ──/decision/laser_cmd──▶ behavior_selector ──/pwm_ctrl──▶ gimbal_executor
                                                                                ├ ch1/ch2/ch3 三色投放舵机
                                                                                └ ch4 激光笔

ground_station_bridge ──UART(/dev/ttyUSB0, 115200, HC-05 蓝牙)──▶ 地面站 STM32C8T6 + TJC 串口屏
                          ($TARGET/$GUIDE/$STAT/$START/$ACK)
```

**与旧框架的关键区别**：此处使用 **10Hz Timer 持续流式发送** MAVLink 位置命令，而非旧框架的"发一次就等"。飞控如果没收到一帧，10ms 后下一帧就到，天然抗丢包，不会出现 30-40 格断连问题。

## 4. 状态机完整设计

### 4.1 状态流转

```
INIT → READY → TAKING_OFF（爬升1.0m→悬停→QR解码出口坐标）
     → PATROLING（蛇形80格搜索, 边飞边检测）
       └─ 发现目标桶 → TARGET_FOUND → DROP_APPROACHING → DROP_DESCENDING
          → DROP_COLOR_CHECK → DROP_RELEASING → DROP_RESUMING → PATROLING（未投完）
       └─ 3桶投完 → ALL_DROPS_DONE → PATH_CALCULATING（A* 选最远目标）
          → GUIDE_STARTING（飞到最远目标上方, 激光关）
          → GUIDE_FLYING（激光开, 沿 A* 路径逐格飞）
          → GUIDE_FINISHING（到达出口格, 激光关）
          → LANDING（4phase: 水平到位→0.5m→0.25m→LAND）→ FINISHED
```

### 4.2 各状态处理逻辑

| 状态 | 触发条件 | 动作 | 转移条件 |
|------|---------|------|---------|
| `INIT` | 节点启动 | 等待航点+定位就绪 | 就绪 → `READY` |
| `READY` | 就绪 | 等待启动命令 | 收到 `$START` 或 `auto_start=true` → `TAKING_OFF` |
| `TAKING_OFF` | 启动 | 蜂鸣3声→GUIDED→解锁→爬升1.0m→悬停等 QR 解码 | `QRResult.valid` 或 15s 超时兜底默认出口 → `PATROLING` |
| `PATROLING` | 到达搜索高度 | 蛇形80格边飞边检测目标桶 | 目标确认 → `TARGET_FOUND`；航点超时20s跳下一格 |
| `TARGET_FOUND` | 目标确认 | 记录颜色/格号，蜂鸣提示 | → `DROP_APPROACHING` |
| `DROP_APPROACHING` | 发现目标 | 1.0m 飞向目标上方，视觉伺服持续修正桶心 | 到达 → `DROP_DESCENDING` |
| `DROP_DESCENDING` | 到达目标上方 | 降到 0.5m，伺服继续（偏移按实际高度缩放） | 到达投放高度 → `DROP_COLOR_CHECK` |
| `DROP_COLOR_CHECK` | 到达投放高度 | 悬停确认颜色 | 确认 → `DROP_RELEASING` |
| `DROP_RELEASING` | 颜色确认 | 发 `drop_cmd(颜色码)` → gimbal 按色选通道释放 | → `DROP_RESUMING` |
| `DROP_RESUMING` | 投放完成 | 升回 1.0m | 3桶投完 → `ALL_DROPS_DONE`；否则 → `PATROLING`（断点续巡） |
| `ALL_DROPS_DONE` | 3桶投完 | 进入引导 | → `PATH_CALCULATING` |
| `PATH_CALCULATING` | 全部投完 | A* 规划最远目标→出口路径 | → `GUIDE_STARTING` |
| `GUIDE_STARTING` | 路径就绪 | 飞到最远目标上方（激光关） | 到达 → `GUIDE_FLYING` |
| `GUIDE_FLYING` | 到达引导起点 | 激光开，沿路径逐格飞 | 到达出口格 → `GUIDE_FINISHING` |
| `GUIDE_FINISHING` | 到达出口格 | 激光关 | → `LANDING` |
| `LANDING` | 引导结束 | 4phase 分段下降 + 黑圆视觉伺服 | 触地 → `FINISHED` |
| `FINISHED` | 降落完成 | 无操作 | — |

### 4.3 目标防重复触发机制

- 确认目标只在 `PATROLING` 阶段进入投放流程，引导阶段不再消费 `target_bucket`；
- 已投目标记录到 `_dropped_targets`（按格号 ±1 格去重），同一格不重复投放；
- `fusion_target_detector_node` 允许同色重确认（不做永久颜色锁），重复/已投目标由状态机按格去重兜底；
- 进入 `PATROLING` 时重置航点计时，避免恢复巡逻时把当前格"超时跳过"。

## 5. 关键设计决策

### 5.1 为什么使用 10Hz Timer 驱动状态机而非回调驱动？

旧框架（2025H/28CRAIC）在回调中 `rospy.sleep()` 阻塞 ROS spin，导致 MAVLink 心跳丢失 → 飞控断连。Timer 驱动确保每 100ms 执行一次 tick，不阻塞 ROS 事件循环，心跳和位置报告持续被处理。

### 5.2 为什么 10Hz 持续流式发送 MAVLink 位置命令？

旧框架"发一次就等到达"的模式：如果飞控没收到那一次丢包，就永远等不到 → 断连。10Hz 流式发送：飞控每 100ms 收到一帧，丢一帧无所谓，下一帧 100ms 后就到。这是旧框架 30-40 格断连问题的根因解决方案。

### 5.3 为什么目标检测输出偏移量而非绝对坐标？

`fusion_target_detector_node` 是纯感知节点，不持有无人机位置。它只输出桶心相对画面中心的像素偏移（按实际高度与焦距换算为米偏移），由下游 `mission_state_machine_node` 加无人机位置（按图像时间戳对齐的定位历史）换算为绝对世界坐标。这样感知层与定位层完全解耦，感知层可独立测试。

### 5.4 为什么 `mission_planner_node` 使用 latch=True？

规划层生成航点列表后发布一次。如果决策层稍后才订阅，没有 latch 会丢失航点。latch=True 确保最后一条消息被缓存，新订阅者立即收到。

### 5.5 为什么 `safety_supervisor_node` 独立于 `safety_monitor_node`？

`safety_monitor_node` 在决策层，依赖 `/mission_status`。如果状态机卡死，它可能也无法响应。`safety_supervisor_node` 直接订阅定位层 `/localization/uav_state`，形成旁路监控，把危险状况发布为 `SafetyEvent(CRITICAL)`；紧急降落动作由 `mission_state_machine_node` 响应 CRITICAL 事件触发（安全链路：safety_supervisor 发布 → 状态机转 LANDING）。它本身不直接控制飞控。

### 5.6 为什么执行层统一用 `gimbal_executor_node` 控制 PWM？

激光笔与三色投放舵机都是 PWM 信号，共用同一个 MAVLink 下发通道（`MAV_CMD_DO_SET_SERVO`）。集中在一个节点经 `/pwm_ctrl` 统一发出，避免多个节点同时写 PWM 导致冲突。`behavior_selector_node` 只发 `/decision/laser_cmd`，投放由状态机发 `/decision/drop_cmd`（颜色码），均不直接接触硬件。

## 8. 通信端点总览

本项目在 D 题实际只有 1 条外部通信链路（G 题的消防车 UART / TCP 地面站 / 树莓派拍照链路保留代码但不启动）：

| 节点 | 通道 | 对端 | 协议 |
|------|------|------|------|
| `ground_station_bridge` | UART 串口蓝牙（HC-05 透传，115200） | 地面站 STM32C8T6 + TJC 串口屏 | `$TARGET/$GUIDE/$STAT/$START/$ACK` |

`use_mock=true` 时不开串口、不阻塞，供无地面站联调。

## 9. 坐标系与场地规范

```
巡逻区域: 50dm (X 宽) × 40dm (Y 深)
网格: 10列 × 8行，每格 5dm × 5dm（X0~X9 × Y0~Y7）
原点: (X0, Y0) 格中心 = (0, 0) dm；起飞点 = (X0, Y0) 左下角
机头朝向: X+（X0→X9）；无人机左侧: Y+（Y0→Y7）
飞行高度: 统一 1.0m（起飞/巡查/引导）；投放高度: 0.5m
禁飞区: 20 格（搜索阶段可飞越，引导阶段 A* 避开）
内部单位: dm（路径规划）/ m（ROS 消息与地面站协议，×0.1 转换）
```
